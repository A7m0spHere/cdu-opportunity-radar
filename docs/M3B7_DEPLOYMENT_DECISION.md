# M3-B.7 生产加载边界与部署决策

日期：2026-10-15，Asia/Shanghai。**决策：NO-GO，不申请立即安装生产插件。** v0.1.1 没有已发现的直接 SDK 不兼容；阻断来自加载路径的全局影响和缺失的运行状态/目录隔离证据。

后续路线和唯一最终补证申请以 [M3-B.8](M3B8_ROUTE_DECISION.md) 为准；本文的多项授权建议保留作阶段记录，不作为继续补证或执行操作的依据。

本轮没有取得新的生产只读授权，**服务器连接次数为 0**。所有生产事实来自 [M3-B.6 报告](M3B6_SDK_READONLY.md)及其已保存、脱敏的证据，属于此前快照，未刷新当前生产状态。本轮仅在本地核对必要调用链、证据完整性和决策条件，不新增插件功能，也不进行安装、加载、启停、容器操作、消息发送或模型调用。

## 2. 钩子、同步与日志的具体边界

下列均为已保存现场源码支持的静态结论，**没有本轮执行证据**。

| 路径 | 范围和副作用 | 对生产的限制 |
| --- | --- | --- |
| `load(specified_dir_name=...)` / 指定模块 load | 只选择目标模块导入/初始化；随后向全局注册表中符合 enabled/activated 条件的 OnPluginLoadedEvent handlers 通知 | 限制导入对象，不限制通知对象；实际回调内容未知 |
| `_terminate_plugin` / 精确停用 | 调用自己的 terminate 后，通知符合条件的 OnPluginUnloadedEvent handlers；自有终止失败时不保证通知完成 | 停用也不是全局无影响的回滚入口 |
| `load` 的公共收尾 | 移除所有 root handlers，并运行 `sync_command_configs()` | 即使只加载一个无命令插件，仍执行这些步骤 |
| 命令同步内部 | 全局命令描述符与 DB 配置绑定；修改运行时命令启用、名称、别名；存在 stale 时调用 `delete_command_configs` | 可能影响 AIHOT/其他插件中存在的命令；不能断言任何具体业务命令已改变；不读聊天 DB 来补证 |
| Web 安装/上传/启停/重载/卸载成功后的公共步骤 | `_sync_skills_after_plugin_change` → 遍历 `session_booter` → available 检查 → skills 同步 | 不按 CDU 插件限定沙箱；无活跃对象时可能不进入同步，但现场集合未知 |
| skills 同步内部 | 临时目录与 ZIP 创建/删除、复制 skills、booter.shell.exec、upload_file、应用/扫描 skills、缓存更新 | 条件下存在上传、Shell 和文件修改；当前不能提供完整影响对象及恢复证据 |
| 未知名称或无名称 reload | 没解析到指定模块时转为全部终止、解绑、清空注册表再 load 全部 | 不用于探测或安装新插件；不能以指定了字符串就当作单插件 reload |

root handler 清理是否损坏现有日志，取决于实际日志拓扑。如果 root 上有现用 stream/file/转发 handler，移除后相关日志可能停止进入原渠道。它不等同于必然关闭全部 AstrBot 日志，也不能因框架另有 logger 就认定无影响。静态配置文件的备份不能恢复进程中已移除的 handler 实例；本轮没有读取或修改它们。

OnAstrBotLoadedEvent、OnPlatformLoadedEvent 与 OnPluginLoadedEvent 为不同事件；单目录 load 不应被描述成必然触发整个机器人启动事件。其他插件的回调若发网络请求、创建任务、写文件或调用模型，其实际行为仍无法从当前未知注册集合推出。

### 状态 GET 也需要先检查调用链

已有脱敏源码提供一项需要收紧的调查建议：`get_plugins` / `get_plugin_detail` 在插件有 logo 时，会经 `get_plugin_logo_token` 调用 `file_token_service.register_file(..., timeout=300)`，并写 `_logo_cache`。因此**不能直接批准“请求插件列表/详情 GET”作为严格无状态修改的检查**。文件令牌服务是否持久写入未核验，不作推断；已知注册/缓存动作本身就超出纯读取。

`get_plugin_handler_components` 能从运行 registry 读取 event_type/name，但它是内部方法；从外部调用它需要进入运行上下文，不能以此建议注入 Python 或导入模块。详情还不等价于完整 enabled/activated 钩子清单。新启动一个 Python 进程读取空 registry、root handlers 或 session_booter，也不能代表正在运行的生产进程。

本轮没有使用这些入口。只重新批准同样的静态源码读取，不能填补运行注册表和活跃沙箱的缺口；不建议反复连接并扩大扫描。

## 3. 数据目录与隔离结论

以下先用 `<DATA_ROOT>` 表示**实际有效数据目录**，不把它默认等同于此前挂载的 `/AstrBot/data`。

| 对象 | 源码推导的预期位置 | 现场证据缺口 |
| --- | --- | --- |
| 插件安装 | `<DATA_ROOT>/plugins/astrbot_plugin_cdu_radar` | 实际根目录、是否已存在、父目录权限/链接未确认 |
| 插件配置 | `<DATA_ROOT>/config/astrbot_plugin_cdu_radar_config.json` | 是否已存在、属主/权限、是否为链接未确认 |
| 专属持久化 | `<DATA_ROOT>/plugin_data/astrbot_plugin_cdu_radar/state.sqlite3` | 目录/库不存在还是已有、属主/权限/链接未确认；不创建目录来验证 |
| AIHOT 数据 | 本轮未确认其有效持久化路径 | 不根据插件名称猜测实际路径；不能证明与新插件无重叠 |
| Docker bind | 先前确认 `/AstrBot/data` 为可写 bind | 宿主源路径只用别名；未确认有效根目录是否落在该 bind 内，以及子路径是否另行解析至其他生产目录 |

`get_astrbot_root` 可能受 ASTRBOT_ROOT / desktop runtime / cwd 影响；PluginManager 在构造时保存安装/配置路径，StarTools 创建目录时再求数据路径。因此 cwd 快照、目录字符串不同、一个可写 bind，均不能单独证明正在运行实例的三个路径有效且隔离。不得实际调用 StarTools（可能创建目录）验证。

**隔离结论：命名设计独立，现场隔离未证明。** 尚不能排除符号链接、已有目录、同 inode/绑定别名或权限问题。需要实际运行身份及有效路径的可信证据，再对路径及必要父级进行只读 lstat/stat/realpath、UID/GID/mode、挂载边界检查；新路径不存在时只检查已存在的祖先，不做写入探针。只输出角色别名和是否重叠，不公开宿主私有目录。

## 4. 三种安装路径比较

| 路径 | 全局步骤/生产组件 | 写入或上传 | 重启与可调用性 | 备份/恢复与证据评价 |
| --- | --- | --- | --- | --- |
| A. 管理界面上传 ZIP | install_plugin_from_file → 精确目录 load → 全局 loaded 通知、root 清理、命令同步；路由成功后再同步活跃沙箱 | 上传 ZIP/解压/重命名/配置生成/可能的依赖处理；条件下 skills 上传/Shell/文件操作；安装还有条件 telemetry 路径 | SDK 设计可热安装，不必然重启；现场运行未验收 | 源码路径已知，动态影响对象未知；只备份新插件文件不足以恢复全局影响；NO-GO |
| B. SDK 指定目录/模块 load | 缩小导入对象，但仍有 loaded 通知、root 清理和命令同步；纯 manager 方法体不包含 Web 的 skills 后处理 | 导入/初始化/配置及公共命令路径仍可能写；导入依赖恢复路径也需保留约束 | 有内部 SDK 方法，不等于已有受支持的外部调用入口；不能通过注入在线 Python 调用它。没有完整安全执行方案 | 静态单插件选择已确认；现场入口、动态影响和恢复未知；NO-GO |
| C. 离线放置文件，再用支持的加载流程 | 文件放置本身不等于加载；后续仍取决于 A/B 或已有精确重载入口。未注册名称 reload 有全量风险 | 放置源码本身就是生产写入；随后保留加载的全局影响；若经 Web 仍有 skills 同步 | 不必然需要重启，但没有经确认的“新目录、只加载它”的外部流程；不能以重启代替未确认路径 | 新文件可事先记录/备份，但回滚加载副作用不能仅删目录；NO-GO |

A 的精确链来自保存的路由 AST 与固定 SDK `install_plugin_from_file`（1819 起）：临时目录 → 解压/元数据目录 → 同名目录冲突检查 → 重命名 → `_ensure_plugin_requirements` → `load(specified_dir_name=...)` → 元数据/条件指标上报；失败会记录失败目录，不能假设所有路径自动恢复原样。候选 ZIP 没有 requirements 文件，但不能据此宣称导入和 SDK 公共处理完全无副作用。

无一条现有证据支持“复制目录绕过全局步骤”。也不能只给新插件加 enabled=false 来阻止其 initialize 之外的 SDK 动作。

## 5. GO / NO-GO 判定

| 用户要求的 GO 条件 | 当前证据是否满足 |
| --- | --- |
| 安装及加载实际调用链明确 | A 静态链明确；B/C 可执行入口及运行分支未确认，未完全满足 |
| 全局副作用范围查明或被限制 | 逻辑范围明确，实际钩子/命令/日志/沙箱对象未知，未满足 |
| 无不可接受的数据修改、上传、Shell | 存在条件上传/Shell 与跨插件命令修改，未证明可限制/接受，未满足 |
| 有效目录与其他插件隔离 | 未满足 |
| 可执行的备份、停止、恢复方案 | 新插件自身有停止机制；全局状态无法保证恢复，未满足 |
| 无需擅自重启生产 | 没有重启计划；尚不能据此认定其他条件通过 |
| 无超预期发送或 LLM 工具 | 本插件离线审查未发现此入口；其他动态回调仍未知，整体未满足 |

**最终 NO-GO，生产安装继续 blocked。** 这不是判定 v0.1.1 无法运行，而是不具备申请受控安装所需的隔离和恢复证据。当前可接受的剩余项，仅包括已明确告知的“SDK True 非 QQ 送达”“跨崩溃不能严格 exactly-once”等候选设计限制；它们也需要未来发送阶段明确接受。未知钩子、潜在全局命令修改、沙箱上传/Shell、目录交叉和日志恢复不能在本轮默认为可接受风险。

推荐保持当前生产原状和 v0.1.1 候选，先确定是否能通过**已经存在且证实纯只读的运行状态渠道**或管理员已有脱敏记录补证。当前材料没有证明存在覆盖全部所需字段的这种渠道；不要为了取得 GO 临时加生产探针、调用管理 GET、修改核心或执行钩子。

## 6. NO-GO 后的独立推送备选

可以另行设计“独立安全 RSS 服务 → 私有 outbox/预算 → 获准的受限消息发送接口”，保留 M3-A 审批版本和 503 防护。本轮只是设计评估，没有连接 OneBot/NapCat、查看其凭据或发送，也没有实现新发送器。

| 约束 | 最低要求和风险 |
| --- | --- |
| 凭据 | 不复用/读取已有 QQ Token 来试探；单独审批凭据来源、存储及撤销。优先单目标、单动作的受限网关；若只能使用权限宽泛的 OneBot Token，必须明确其超出单群发送的能力及泄露影响，不能把它视为已经实现最小权限 |
| 目标 | 管理员配置唯一确定的完整目标，服务端精确白名单；RSS 内容不能提供目标、任意 URL、接口名或凭据。发送器不得有广播/默认群回退 |
| 预算 | 例如累计最多 2 次尝试；在外部调用前可靠提交预算，跨进程锁/单消费者，不因重启、失败或重新部署清零 |
| 去重 | 合法非空 Feed 初始化历史；稳定 GUID 与来源/目标绑定；503/超时/解析失败不推进水位；拒绝静态旧 Feed 回退 |
| 故障 | 超时、取消、连接断开后可能已经送达，记录 uncertain 并保留预算，不自动补发；只把明确失败纳入有上限的重试，不承诺 exactly-once |
| 回滚 | 先停止专属 sender/禁用新凭据，再停 RSS；保留 outbox 和消耗预算。移除 RSS 或撤销审批不能撤回已发送 QQ 消息；更正需独立授权 |
| 网络/资源 | 新凭据、消息接口和隔离路径引入新的信任边界；不擅自开放端口、共享生产卷或改变 AstrBot/NapCat 网络。其可行性尚未现场核验 |

这条路线避免 AstrBot 插件加载的公共步骤，但新增了凭据和投递实现的维护负担，**不自动获得 GO**。若现有消息接口无法授予受限权限，仍应维持 NO-GO，不能为了省插件加载审查而把完整机器人控制权交给 RSS 容器。

## 7. 下一阶段的精确授权项目

本轮到此停止，不要求把以下项目合并批准。

1. **仅补证的生产只读检查**：限定此前主机/现有 AstrBot，查询确切容器身份、镜像、进程 UID/GID、必要 mount 目标；仅对管理员先确认的有效数据根、plugins/config/plugin_data 及 CDU/AIHOT 必要路径做存在性、链接、属主和权限检查。不读文件内容、凭据、环境变量、聊天 DB，不写权限/目录。若有效根无法安全确认或出现非预期链接，停止对应项。
2. **动态状态渠道的单独确认**：先由管理员给出已经存在的脱敏运行状态/记录；所需字段仅为 plugin activated、handler event/name/enabled、root handler 类型与恢复方式、沙箱实例数量/可用性及 skills 同步状态。若拟调用状态接口，必须先审查精确路由及完整调用链、证明不注册令牌/写缓存/触发同步，再单独批准读取字段；当前不推荐对已发现的插件列表/详情入口直接授权。无法纯只读获得就记录未知并维持 NO-GO，不注入进程或创建生产探针。
3. **如果考虑直接发送备选**：仅先批准离线方案/Mock 合同，不授予 OneBot 网络访问或凭据读取。以后另批受限消息能力、唯一目标、网络、凭据、预算和停止方案；不得沿用本轮授权发送。
4. **只有重新评审得到 GO 后**，才分别申请精确镜像/资源/网络的 RSS 构建运行、固定 ZIP 的默认禁用安装、唯一会话启用、累计最多两次合成发送。当前不申请执行这四项。

不建议“再读更多无关插件源码”。若无法取得所需动态/目录证据，现阶段就接受 NO-GO，而不是增加不确定的生产操作。

## 8. 最小备份与恢复合同

这是未来审批的前置合同，**本轮不执行备份或恢复**，也不声称已有可直接运行的生产回滚命令。

1. 安装前固定源码/ZIP 哈希、唯一目录、有效运行用户和原始状态。确认新插件目录/配置/ledger 是否原本存在；存在则只在单独授权下备份该插件的文件和元数据，不覆盖已有内容。没有现存文件则记录不存在。
2. 全局命令同步未被限制时，需要管理员批准仅命令配置范围的一致性快照、相关运行时命令状态及有条件恢复方案。实际表名、主键、并发变化尚未核验，不能猜 SQL；不能为此复制、回滚或替换含聊天/其他业务状态的整份生产 DB。没有安全的范围快照/恢复路径就不安装。
3. root 日志 handlers 必须有管理员确认的重建/恢复方法；保存日志文件不等于保存 handlers。沙箱若可能同步，需要独立授权的同步对象、版本及恢复方案；未知对象不能靠备份新插件目录覆盖。任一项无法恢复则不采用相应安装入口。
