# M3-B.8 最终有界补证与路线收敛

2026-10-15，Asia/Shanghai。

**决策：生产专用插件 NO-GO；独立 OneBot 自动发送也尚不具备 GO 条件。推荐暂时保留人工审批与 RSS 发布能力，不启用自动 QQ 推送。** 自本决策起，停止围绕生产插件加载的后续开发、扩展扫描和反复补证；只有未来出现新的实质证据，才重新评审。

本轮没有服务器访问授权，服务器/NapCat 连接、管理接口调用、插件加载、容器操作、QQ 发送和模型调用均为 0。本文只整理已有证据与一份**未执行的最终检查申请**，不批准任何部署或网络变更。RSS 方案的选择也不表示服务器 RSS 已部署或获准开放公网。

### 已知全局副作用是否可接受

不能以“插件没有缺陷”代替这项判断，也不把所有框架公共动作一律判为不可接受。

| 副作用 | 在何种证据下可以考虑接受 | 当前结论 |
| --- | --- | --- |

| 命令同步 | 完整运行 handler 与配置范围已知，证明无意外 stale 删除/跨插件启用或改名，或有经认可的有界恢复方案 | 未证明；不能仅凭“通常幂等”接受 |

## 唯一检查申请 R1：最终有界补证（未申请执行、未获批准）

本节是本轮唯一一份额外现场检查申请草案，覆盖三个阻断项；不另附 NapCat 探测申请。**获准前不连接。即使获准，也先满足入口条件，不满足则不开展服务器检查。**

### 入口条件与执行上限

- 仍为此前确认的同一 Linux 主机、确切现有 AstrBot 容器和主应用 PID，由管理员确认；身份不匹配停止，不转向其他实例。
- 管理员先提供已经存在的脱敏动态状态材料、有效数据根及 AIHOT 实际持久化路径来源，以及已有的全局恢复依据。不能为补证要求刷新插件管理页、创建探针、导入模块、注入在线 Python 或临时新增接口。
- 当前证据没有证明存在覆盖所需字段的纯只读状态入口。因此本申请**不包含任何 AstrBot HTTP 请求**，尤其不包含插件列表/详情 GET；其源码可能注册 logo 文件令牌并改缓存。不得用新的 Python 进程中的空 registry/root logger/session_booter 冒充生产运行状态。
- 若没有可信动态材料或可信全局恢复依据，直接结案为“未知 / NO-GO”，**不为补目录元数据先登录一次**。这是避免无限补证的第一停止点。
- 条件满足且另获明确批准后，仅一轮、最多一次检查会话，10 分钟或下表范围耗尽即止；无递归目录扫描、无失败重试扩容、无 API/端口连通探针、无写入探针。材料过期或不对应当前实例时不据此给 GO。

### 固定目标、字段、方法与停止条件

`<DATA_ROOT>` 必须由管理员事先给出有效绝对路径和依据，不从完整环境变量、配置、聊天数据库推测。`<APP_PID>` 也须先确认。变量未确定即不执行，不能自动搜索替代。

| 目标文件/对象 | 仅取字段 | 只读方式与边界 | 停止条件 |
| --- | --- | --- | --- |
| 确切 AstrBot 的 Docker 元数据 | ID/镜像 ID、State.Status、Config.User、WorkingDir、ReadonlyRootfs；相关 mounts 的目标/类型/RW，宿主 source 仅映射别名 | 格式化白名单字段；不输出完整 inspect/Env/启动参数 | 身份或镜像与被审材料不对应，停止并保留 NO-GO，不重读整套源码 |
| `/proc/<APP_PID>/status`、`/proc/<APP_PID>/cwd` | Uid/Gid/Groups、cwd 的路径角色 | 只读状态字段和 readlink；不读 environ/cmdline/fd 内容 | PID/运行身份不明或权限异常即止，不用新 exec 进程的 UID 冒充应用身份 |
| `<DATA_ROOT>`、其 plugins/config/plugin_data 三个父目录 | exists、lstat/stat 的 UID/GID/mode/dev/inode、realpath、是否 symlink、是否落入批准 mount | 只检查列出的目录及解析所必需的已批准祖先；不列目录内容、不读配置 | 路径不在批准边界、未预期 symlink/mount 或祖先不可确认则停止；不继续跟进外部关键目录 |
| `<DATA_ROOT>/plugins/astrbot_plugin_cdu_radar`；`<DATA_ROOT>/config/astrbot_plugin_cdu_radar_config.json`；`<DATA_ROOT>/plugin_data/astrbot_plugin_cdu_radar` 及其 `state.sqlite3` | 同上，加不存在/已有的明确区分 | 不打开 JSON/SQLite，不建文件。新路径不存在仅检查已存在的父级；不以 os.access 的探针身份证明应用可写 | 发现已有非预期状态、链接、重叠或无法确定权限则止；不删除、接管或修权限 |
| 管理员事先明确的 AIHOT 持久化路径，最多 3 个 | 同样的路径元数据和与 CDU 路径的重叠布尔值 | 不读 AIHOT 配置/数据/日志；宿主路径仅用角色别名，不猜数据目录 | 无实际路径证据、发现重叠或边界外解析即止 |
| `/AstrBot/astrbot/core/db/sqlite.py` | 仅 `get_command_configs`、`delete_command_configs` 的签名/AST 及它们直接使用的 ORM 表/键引用、文件 SHA-256 | 标准库解析必要源码，不导入、不实例化 db_helper；最多该文件 1 MiB | 文件不存在/非标准布局、需追入其他文件或 DB 才能确认则记录未知并止，不扩展调用链扫描 |
| 管理员已提供的动态状态材料（本地，不新调用生产接口） | 实例/时间；plugin activated；handler event/name/enabled/所属插件；root handler 类型、level、过滤/转发依赖；沙箱数量/可用性、同步是否可跳过及依据 | 只处理脱敏材料，不取回调对象 repr、完整群会话标识、命令正文、凭据或沙箱文件 | 缺字段、来源不可信、仅静态配置/目录列表、非正在运行实例，或回调副作用不明，均保持未知 |
| 管理员已有的恢复依据（本地） | 命令记录范围/一致性/并发保护；handler 重建方法；沙箱同步对象与恢复方式；隔离环境演练版本/结果 | 只审已有文档与脱敏演练证据，不读取生产 DB、不在本次创建备份、更不试恢复 | 仅有“已备份整个 data/DB”、需要全量重启、无法处理并发或沙箱影响不明，判不满足 |

POSIX mode、UID/GID 和 RW mount 只能给静态权限证据；ACL、容器安全策略或运行身份不清时不冒充已验证可写。不得以创建文件/SQLite 连接试验补齐结论。实际配置根与 ledger 根若不一致，也不能只核对其中一处。

### 输出与结束规则

仅形成一份脱敏矩阵：每个条件 `已证明 / 未知 / 不满足`，记录时间、实例标识摘要、所查路径角色、哈希和停止原因，不保存业务数据。任何关键项未知/不满足，R1 结束仍为 NO-GO；不转向试加载、扩大扫描或第二轮同类检查。

如果全部满足，只表示可以另行重新评审是否申请受控安装；R1 不授权安装、备份写入、恢复、禁用业务、容器操作或消息发送。现阶段没有执行 R1 的必要入口材料，也没有批准。

## 全局备份/恢复的最低可信门槛

1. **命令配置**：明确实际记录/主键、运行 handler 与配置对应关系，有一致性快照和并发校验，恢复只针对受影响记录；不回滚整份含聊天和其他业务状态的生产 DB。当前没有表级现场数据或可执行恢复证据，不能编造 SQL。
2. **日志 handlers**：确认类型、配置和转发/过滤依赖，能在不重启整个生产机器人的条件下恢复；需有匹配 SDK 的隔离演练或既有运维证据。仅保存日志文件、配置文本或 handlers 的字符串表示不足。
3. **沙箱**：要么证明所选受支持入口不执行同步，要么明确全部受影响对象、上传/Shell/文件变更和恢复方法；不能因某时刻数量为零就默许同步。当前无法证明。
4. **插件自身**：路径独立、默认 disabled；停用必须确认自己的 task/client/lock 退出，保留 ledger 和已消耗预算。源码卸载成功不证明清理成功，且停用/卸载本身仍有全局路径。

目前不具备这三类全局恢复能力的可信证据。因此不以“先备份再试安装”作为方案，也不开始实现针对未知生产状态的恢复工具。

## 独立 RSS → OneBot 发送器：离线可行性

**可以在设计上避免安装 AstrBot 插件，但尚未证明能使用当前 NapCat 独立发送。** 没有连接 NapCat、读取 Token 或调用任何动作。

| 必须评估的项目 | 已有证据/缺失 | 技术判断 |
| --- | --- | --- |
| 实际版本与接口 | 先前容器镜像标签 v4.15.0、健康快照；实际 app 版本未核实。档案仅有 NapCat 向 AstrBot 反向 WS 的历史线索 | 未证明当前启用了可供独立客户端使用的 HTTP/正向 WS 动作服务，也没有其监听、路径或返回契约证据 |
| 反向 WS | 连接目的端是 AstrBot 的接收端；现有连接并非独立 sender 已获授权的连接 | 不复用/劫持其 socket，不把 AstrBot 的 WS 端口当作 NapCat HTTP 动作端点；不假定可再连第二个客户端 |
| 认证 | 未读取 access token，认证启用、作用域和撤销能力均未知 | 不猜 Token、不尝试无认证探测，不建议暴露未认证 HTTP。若接口只提供宽权限 Token，则 sender/受限网关泄露可影响整个机器人，不能宣称已实现单群权限 |
| 网络隔离 | 先前 AstrBot/NapCat 为同一 bridge、不同命名空间；bridge internal=false | 不等于新容器已连通或允许访问，不等于容器间可共用 127.0.0.1。优先经批准的内网受限端点/窄网关，不发布公网端口；可能需要新增 NapCat 入口或网络控制，均属另行生产变更 |
| 唯一会话白名单 | 本轮无获准目标、无消息能力 | sender 配置固定机器人身份、group/private 类型、唯一数字目标；网关如采用也强制相同白名单与单一 send 动作。RSS 不提供目标/动作/接口 URL，不允许广播或回退 |
| 凭据隔离 | 方案未实现 | sender 最好只持受限网关凭据；宽权限上游 Token 留在更受控的网关。若做不到，应明确风险而非虚构原生权限。凭据限权限存储、日志脱敏、独立撤销；不挂生产配置卷 |
| 持久发送预算 | 可参考既有 engine 的状态机，但未实现独立 sender | 外部调用前事务提交累计尝试数；初始上限 2、默认重试 0、单消费者/跨进程锁；失败/不确定消耗预算，重启或部署不清零。复用设计不能当作代码已可运行 |
| 去重和有效性 | M3-A 守门 RSS/稳定 GUID 已有离线验证 | 合法非空合成种子只初始化；来源+目标绑定持久 GUID。503/解析失败不推进状态，不用旧 XML；每次投递前重新确认仍有效，无法确认则停发。已在途消息无法因撤销追回 |
| 故障恢复 | 无实际 sender/接口验收 | 超时/断线/取消后可能已送达，记录 uncertain、不自动重发，保留预算；动作成功响应与测试会话观察分开，不承诺跨崩溃 exactly-once。重启不能集中补发历史 |
| 停止与回滚 | 无部署 | 先停止新增 sender/撤销其专属能力，再停止新增 RSS；保留 outbox/ledger。不影响已有反向 WS、AIHOT、AstrBot/NapCat，不尝试撤回群消息；新端点如曾配置，另按获准方案撤销 |

若现有 NapCat 没有合适的受认证动作入口，独立 sender 就需要额外配置或受限网关，不能称为“零生产修改”。若必须断开原反向 WS、重启现有组件、共享完整配置卷或开放无认证入口，当前方案同样 NO-GO。

本轮不提交第二份 NapCat 现场检查申请。未来只有管理员给出新的脱敏接口/认证/网络实质证据，并明确选择该路线后，才另定独立范围；不因此重新启动插件加载调查。

## 路线排序与最终决策

以下按当前生产影响和证据充分程度给出综合顺序；资源是设计预算/相对判断，不是新的服务器实测。原先约 1.7 GiB 可用内存、256 MiB RSS 容器限额只能作历史容量线索，不能当成已运行或足够容量的证明。

| 综合顺序 | 路线 | 生产风险 | 需要修改的既有组件 | 资源开销 | 维护成本 | 决策 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 保留人工批准 RSS，暂不自动 QQ | 最低新增风险，不涉及机器人加载/发送 | 本轮无；未来若部署 HTTP 服务仍需独立授权 | 当前保留本地 CLI/Feed 无新增常驻进程；服务器 RSS 仍只是既有 ≤256 MiB 草稿预算 | 最低，复用既有审批/守门 HTTP | **路线选择 GO**；不等于批准任何服务器部署或公开端口 |
| 2 | 独立 RSS → 受控 OneBot sender | 避开 AstrBot 加载全局动作，但当前接口/认证未知；宽 Token 或不安全网络可能比插件更危险 | 不装 AstrBot 插件；可能需 NapCat 入口、窄网关、网络/凭据变更，尚未确认 | RSS 加 sender 的任务/outbox，若有网关再增资源；未测，不新增 AstrBot/NapCat 实例 | 高，需要实现/验收认证、状态机、限额和运维 | **生产 NO-GO，保留离线备选**；不立即开发或部署 |
| 3 | 继续生产专用 AstrBot 插件 | 已知跨插件命令/日志影响，动态钩子和沙箱/恢复未知 | 新插件/专属配置，加上无法排除的全局运行状态影响 | RSS 加现有 AstrBot 内一个消费者；增量可能低于独立 sender，但资源低不抵消生产风险 | 插件代码已存在；生产加载/恢复维护风险最高 | **NO-GO，冻结后续加载相关开发** |

这是综合选择，不表示独立 sender 在每个维度都优于插件：它的新增实现维护成本通常更高，其认证/网络证据目前也更少。三条路线中，当前只有“不启用自动 QQ”的路线满足本轮不改生产的边界。
